# Topic: Design Amazon: Online Shopping System
**Archetype:** arch_01 (High-Volume Transactional / E-commerce)

**Component_Mapping:**
- **Component:** "Product Catalog" | **Tech:** "Elasticsearch / CloudSearch" | **Rationale:** "Enables high-performance full-text search and faceted filtering (category, price, rating) across millions of SKUs."
- **Component:** "Shopping Cart" | **Tech:** "Redis / DynamoDB" | **Rationale:** "Provides low-latency access to transient session data; ensures the cart is highly available even if the main order DB is lagging."
- **Component:** "Order Management" | **Tech:** "MySQL/PostgreSQL (Sharded)" | **Rationale:** "Requires ACID compliance to ensure transactional integrity during the checkout process and prevent double-charging."
- **Component:** "Inventory Service" | **Tech:** "Distributed Lock / Redis" | **Rationale:** "Manages real-time stock levels and prevents overselling during high-traffic flash sales via atomic decrements."
- **Component:** "Payment Gateway" | **Tech:** "Stripe / Braintree Integration" | **Rationale:** "Securely processes transactions and handles PCI-compliance; integrated via asynchronous webhooks for order status updates."

**Data_Model:**
- **Product_Table:** `{product_id: uuid, name: string, description: text, price: decimal, stock_count: int}` (Partitioned by Category)
- **Order_Table:** `{order_id: uuid, user_id: uuid, status: enum, total_amount: decimal, items: json_blob}` (Sharded by UserID)
- **Inventory_Log:** `{sku_id: uuid, change: int, transaction_id: uuid}`

**Flow_Logic:**
- [Search] -> [Search Service] -> [Elasticsearch] -> [Product Details]
- [Add to Cart] -> [Cart Service] -> [Redis Cache]
- [Checkout] -> [Order Service] -> [Inventory Check] -> [Payment Gateway] -> [Update Order Status] -> [Kafka Event]
- [Post-Checkout] -> [Kafka] -> [Warehouse/Shipping Service] -> [Email Notification]

**Scaling_Strategy:**
- **Inventory Scaling:** Use a "Reserve-then-Commit" pattern to lock inventory during the 10-minute checkout window.
- **Database Scaling:** Shard the Order Database by `user_id` to ensure that all orders for a single user are co-located, optimizing "My Orders" query performance.
- **Traffic Spikes:** Implement "Queue-it" or buffer requests in SQS during flash sales to protect downstream checkout services from saturation.

**Connectivity:**
- ["User", "API Gateway"]
- ["API Gateway", "Search Service"]
- ["Search Service", "Elasticsearch"]
- ["Order Service", "Inventory Service"]
- ["Order Service", "Payment Gateway"]
- ["Order Service", "Kafka"]
- ["Kafka", "Shipping Service"]




# Topic: Designing an API Rate Limiter
**Archetype:** arch_03 (Security & Traffic Governance)

**Component_Mapping:**
- **Component:** "Request Interceptor" | **Tech:** "API Gateway (Envoy / Kong)" | **Rationale:** "Acts as the entry point to intercept incoming requests and enforce limits before they reach backend services."
- **Component:** "Rate Limit Engine" | **Tech:** "Token Bucket / Sliding Window Algorithm" | **Rationale:** "Calculates if a request is within the allowed threshold based on pre-defined user or IP quotas."
- **Component:** "Distributed Counter" | **Tech:** "Redis (In-Memory)" | **Rationale:** "Stores real-time request counts and timestamps; chosen for atomic increments (INCR) and high-speed lookups."
- **Component:** "Rule Config Store" | **Tech:** "Relational DB (PostgreSQL) + Local Cache" | **Rationale:** "Stores per-tier or per-API limits; cached locally at the gateway to avoid DB roundtrips for every request."

**Data_Model:**
- **Rate_Limit_Key:** `Key: {user_id:api_endpoint} | Value: {count:int, start_time:timestamp}`
- **Rules_Config:** `{client_tier: string, rps_limit: int, burst_size: int}`

**Flow_Logic:**
- [Request Received] -> [API Gateway] -> [Extract User Identifier] -> [Query Redis Counter]
- [Decision Engine] -> [If Count < Limit: Increment Counter & Forward] -> [If Count >= Limit: Return 429 Too Many Requests]
- [Background] -> [Sync Redis Replicas] -> [Update Rule Cache from Config DB]

**Scaling_Strategy:**
- **Local vs Global:** Implement local caching of counters for extremely high-traffic endpoints to reduce Redis contention (hybrid rate limiting).
- **Partitioning:** Shard Redis cluster by `user_id` to ensure counters for a specific user are always handled by the same node, preventing race conditions.

**Connectivity:**
- ["User", "API Gateway"]
- ["API Gateway", "Redis Cluster"]
- ["API Gateway", "Rule Config Store"]
- ["API Gateway", "Backend Services"]

# Topic: Designing an E-ticketing Service
**Archetype:** arch_05 (High-Concurrency Transactional)

**Component_Mapping:**
- **Component:** "Virtual Waiting Room" | **Tech:** "Redis-based Queue / Cloudflare Waiting Room" | **Rationale:** "Protects downstream services during 'on-sale' surges by throttling user access to the booking engine."
- **Component:** "Seat Reservation Engine" | **Tech:** "Distributed Locking (Redis/Redlock)" | **Rationale:** "Ensures 'Exclusive Lock' on specific seats for a 5-10 minute window to prevent double-booking during checkout."
- **Component:** "Event Metadata DB" | **Tech:** "PostgreSQL (Sharded by EventID)" | **Rationale:** "Provides ACID compliance for seat maps and ticket status; sharding by EventID prevents 'Hot Event' contention from affecting other events."
- **Component:** "Payment Orchestrator" | **Tech:** "Stripe/Adyen + SQS" | **Rationale:** "Handles complex checkout flows; uses SQS to ensure that if the payment succeeds, the ticket is asynchronously generated and sent."

**Data_Model:**
- **Seat_Status:** `{event_id: uuid, seat_id: string, status: enum(Available, Locked, Sold), lock_expiry: timestamp}`
- **Ticket_Entity:** `{ticket_id: uuid, user_id: uuid, event_id: uuid, qr_code_hash: string}`

**Flow_Logic:**
- [User Search] -> [Event Cache (Redis)] -> [Display Seat Map]
- [Select Seat] -> [Distributed Lock (10m TTL)] -> [Update Status: Locked]
- [Payment Success] -> [Update Status: Sold] -> [Clear Lock] -> [Generate Ticket]
- [Lock Expired/Payment Fail] -> [Revert Status: Available]

**Scaling_Strategy:**
- **Concurrency Control:** Use pessimistic locking for seat selection but optimistic locking for general user profile updates to maximize throughput.
- **Read Scaling:** Use read-replicas and CDNs for static event details and seat map images to offload the primary database.

**Connectivity:**
- ["User", "Waiting Room Service"]
- ["Waiting Room Service", "Booking Service"]
- ["Booking Service", "Redis (Distributed Lock)"]
- ["Booking Service", "PostgreSQL (Event DB)"]
- ["Booking Service", "Payment Gateway"]

- **Component:** "Media Storage" | **Tech:** "Object Store (S3) + CDN (CloudFront)" | **Rationale:** "Decouples binary image/video data from metadata; CDN ensures low-latency delivery to a global user base."

**Data_Model:**
- **User_Feed:** `Key: UserID | Value: [ {PostID, Timestamp}, ... ]` (Stored in Redis)
- **Follow_Graph:** `Source_UserID | Destination_UserID | Timestamp` (Partitioned by Source_UserID)
- **Post_Metadata:** `{PostID, UserID, Content_URL, Lat/Long, Timestamp}`

**Flow_Logic:**
- [Post Tweet/Photo] -> [Write to Metadata DB] -> [Push to Fan-out Queue]
- [Fan-out Worker] -> [Identify Followers] -> [Update Followers' Redis Timeline Caches]
- [User Pulls Feed] -> [Read Redis Timeline Cache] -> [Hydrate Post Details from Metadata DB/Cache]

**Scaling_Strategy:**
- **Hybrid Fan-out:** Use "Push" (Write-side) for users with <5k followers; use "Pull" (Read-side) for Celebrities to prevent the system from trying to update 50M Redis caches simultaneously.
- **Active User Optimization:** Only pre-compute timelines for users who have logged in within the last 30 days to save memory.

**Connectivity:**
- ["User", "API Gateway"]
- ["API Gateway", "Feed Service"]
- ["Feed Service", "Timeline Cache (Redis)"]
- ["Fan-out Worker", "Timeline Cache (Redis)"]
- ["Post Service", "Metadata Store (Cassandra)"]




# Topic: Real-time Keyword & Hashtag Search
**Archetype:** Search_01 (High-Ingestion Search)

**Component_Mapping:**
- **Component:** "Ingestion Pipeline" | **Tech:** "Kafka + Storm/Flink" | **Rationale:** "Streams new tweets/posts into the search indexer in real-time, enabling 'Trending Topic' detection within seconds."
- **Component:** "Search Indexer" | **Tech:** "Elasticsearch / Lucene Shards" | **Rationale:** "Maintains an inverted index of keywords/hashtags; sharded by TweetID to distribute the heavy write-load of new posts."
- **Component:** "Aggregator Service" | **Tech:** "Distributed Scatter-Gather" | **Rationale:** "Queries all search shards in parallel and merges the most relevant/recent results before returning to the user."

**Data_Model:**
- **Inverted_Index:** `Term: #Hashtag | List: [TweetID_1, TweetID_2, ...]`
- **Trending_Buffer:** `Key: Word | Value: Count_Last_5_Mins` (Stored in Redis for real-time ranking)

**Flow_Logic:**
- [New Tweet] -> [Kafka] -> [Search Indexer] -> [Update Shards]
- [User Searches Keyword] -> [Search API] -> [Scatter query to all Shards] -> [Gather & Rank Results] -> [Return to User]

**Scaling_Strategy:**
- **Time-based Sharding:** Create new search indices daily or hourly. Older indices can be moved to cheaper storage as the relevance of old tweets decreases.
- **N-gram Indexing:** Support partial word searches and autocomplete by indexing word prefixes.

**Connectivity:**
- ["User", "Search API"]
- ["Search API", "Elasticsearch Cluster"]
- ["Kafka", "Search Indexer Service"]

- **Component:** "Matching Engine" | **Tech:** "Distributed Scheduler" | **Rationale:** "Orchestrates the rider-to-driver assignment based on proximity, ETA, and driver rating."

# Topic: Designing a Web Crawler
**Archetype:** arch_08 (High-Parallelism Data Collection)

**Component_Mapping:**
- **Component:** "URL Frontier" | **Tech:** "Distributed Priority Queue (RabbitMQ / Kafka)" | **Rationale:** "Manages the list of URLs to be crawled; prioritizes based on page rank and ensures politeness (wait times per domain)."
- **Component:** "HTML Fetcher" | **Tech:** "Headless Browsers / Async HTTP Clients" | **Rationale:** "Downloads page content at scale while respecting robots.txt and handling dynamic Javascript rendering."
- **Component:** "Content Deduplicator" | **Tech:** "Bloom Filter / SimHash" | **Rationale:** "Efficiently checks if a page's content or URL has already been processed to prevent infinite loops and redundant storage."
- **Component:** "Link Extractor" | **Tech:** "HTML Parser (BeautifulSoup / Cheerio)" | **Rationale:** "Parses fetched pages to discover new URLs and adds them back to the URL Frontier."

**Data_Model:**
- **Crawl_Status:** `{url_hash: long, status: enum, last_crawled: timestamp, content_hash: string}`
- **Domain_Politeness:** `{domain: string, last_access: timestamp, delay_ms: int}`

**Flow_Logic:**
- [Scheduler] -> [Pop URL from Frontier] -> [Check Politeness] -> [Downloader Fetch]
- [Downloader] -> [Deduplicate] -> [Store Content] -> [Extract Links] -> [Push New URLs to Frontier]

**Scaling_Strategy:**
- **Distributed Coordination:** Use a central coordinator (Zookeeper) to manage domain-level locks so multiple crawlers don't hit the same server simultaneously.
- **DNS Caching:** Maintain a high-performance local DNS cache to avoid resolving the same domain thousands of times during a crawl.

**Connectivity:**
- ["Scheduler", "URL Frontier (Queue)"]
- ["URL Frontier", "Downloader Fleet"]
- ["Downloader", "Deduplication Service (Redis)"]
- ["Downloader", "Storage (HDFS/S3)"]






# Topic: Designing YouTube or Netflix
**Archetype:** arch_01 (Ultra-High Read Volume / Media)

**Component_Mapping:**
- **Component:** "Transcoding Pipeline" | **Tech:** "Distributed Workers (FFmpeg / AWS Elemental)" | **Rationale:** "Converts uploaded raw video into multiple resolutions (1080p, 720p, 4K) and formats (HLS/DASH) for cross-device compatibility."
- **Component:** "Video Storage" | **Tech:** "Object Store (S3 / GCS)" | **Rationale:** "Stores multi-terabyte video files with high durability and accessibility."
- **Component:** "Metadata Service" | **Tech:** "MySQL (Read Replicas) / Vitess" | **Rationale:** "Manages video titles, descriptions, view counts, and comments; optimized for a 200:1 read:write ratio."
- **Component:** "Content Delivery" | **Tech:** "CDN (Akamai / CloudFront)" | **Rationale:** "Caches video chunks at the network edge to provide buffer-free playback for global users."

**Data_Model:**
- **Video_Metadata:** `{video_id: uuid, user_id: uuid, title: string, s3_url: string, view_count: counter}`
- **Video_Chunks:** `{video_id: uuid, resolution: string, chunk_index: int, cloudfront_url: string}`

**Flow_Logic:**
- [Upload] -> [API Gateway] -> [Storage (Raw)] -> [Transcoding Queue]
- [Transcoding] -> [Generate Chunks] -> [Upload to S3] -> [Update CDN Cache]
- [View] -> [Client Request] -> [Fetch Metadata] -> [Stream Chunks from Nearest CDN Node]

**Scaling_Strategy:**
- **Chunk-Based Streaming:** Use Adaptive Bitrate Streaming (ABR) to switch video quality dynamically based on the user's current internet speed.
- **Write-Optimization:** Use a "Write-Back" cache for view counts (batch update the database every 1000 views) to prevent the metadata DB from being crushed by popular videos.

**Connectivity:**
- ["User", "CDN (Edge)"]
- ["CDN", "Object Store (Origin)"]
- ["Transcoder", "Object Store"]
- ["Metadata Service", "Read-Replica DB"]
